# Goink 对标调研：架构对比与借鉴点

日期：2026-07-01
调研对象：[sigpanic/goink](https://github.com/sigpanic/goink)（41★，"Goink 桌面 AI 小说创作助手"）

## 一、Goink 是什么

一个 **单用户桌面端 AI 写作助手**（Go + Wails v2 + React，跨平台单文件安装包），定位是"人机对话式协作写作"，不是自动化流水线：

- **Agent 引擎**：自研 ReAct 循环，LLM 自主决定调用哪个工具（31 个结构化工具，覆盖角色/伏笔/正文读写/状态更新），而不是固定阶段顺序执行。
- **结构化记忆**：角色档案+关系图谱、伏笔（目标回收章节/重要程度/超期告警）、故事弧线（节点链）、地点世界观（层级+空间连通）、读者认知状态（谁知道什么）。
- **本地语义搜索**：BGE 中文向量模型（ONNX int8 量化）+ sqlite-vec，支持"按含义查找"而非关键词匹配，全程离线。
- **Skill 系统**：内置/用户/小说 三层覆盖 × 智能/指令/常驻 三种触发模式，8 个内置技能（节拍、潜台词、节奏、钩子、角色设计、打磨、去 AI 味、共创）。
- **维护三重保障**：系统提示词强制"写完必须维护状态" + 动态注入检查清单 + 独立审稿 Agent 比对内容与状态一致性。
- **安全网**：Git 自动 commit/diff/revert，编辑前 diff 预览需用户确认，正则白名单路径沙箱。

## 二、与本框架（bestseller）的核心差异

| 维度 | Goink | bestseller |
|---|---|---|
| 使用场景 | 人机对话协作，单本、单用户 | 无人值守批量生成，服务端流水线 |
| 生成控制 | LLM 自主 ReAct 决策调用工具 | 固定分阶段流水线（构思→大纲→场景卡→正文→39+ 道质量闸门→审计修复） |
| 角色/伏笔/世界观状态 | ✓ 结构化追踪 | ✓ 已有（`domain/story_bible.py`、`payoff_ledger_gate.py`、`WorldSpecInput`、`CharacterKnowledgeStateInput`），且更细（心理侧写/反派魅力档案/社会关系网络） |
| 已建立事实的一致性检索 | ✓ 神经语义向量（BGE + sqlite-vec） | 有检索基建（`services/retrieval.py`：hybrid lexical+vector+structural 打分），但向量部分是**哈希 n-gram 词袋**，不是真语义嵌入 |
| 技能/方法论注入 | 3 层×3 触发模式 | 已有对应物（`concept_methodology_agent.py` 方法论选型 + `quality_levers/` 54+ 文采技法 + `story_effect_skills.py` 效果技能目录，含 use_when/avoid_when/best_stage/conflicts_with），成熟度相当甚至更结构化 |
| 写后一致性维护 | 独立审稿 Agent 比对状态 | `audit_loop.py` + `autonomous_book_repair.py`：确定性闸门扫描 + 自动生成修复任务循环，效果类似但是规则驱动非 Agent 判断 |
| 版本安全网 | Git 自动 commit + diff 预览 + 用户确认 | 数据库版本号（`PlanningArtifactVersionModel`/`ChapterDraftVersionModel`）+ 重写任务审计轨迹，无 git、无 diff 预览、无人工确认 |

**结论**：两者定位不同（协作工具 vs 批量生产管线），本框架在"结构化记忆颗粒度"和"技能体系结构化程度"上不逊于甚至强于 goink。真正的、具体的、可验证的差距只有一处：**一致性检索用的是词袋哈希而非真语义嵌入**。

## 三、可借鉴点评估

1. **真语义嵌入替换哈希词袋检索**（已验证，见下方 POC）—— 高价值，风险可控，直接复用现有 hybrid 打分框架的接口形状。
2. **Git diff-预览+人工确认再落盘** —— 对无人值守批量流水线意义有限（本框架就是要去掉人工确认这一环），不建议引入；数据库版本号+重写任务审计已覆盖"可回滚"这个诉求。
3. **纯 Agent 自主决策 ReAct 循环替代固定流水线** —— 对小说生成这种需要强一致性、强质量闸门的批量生产场景风险过高（LLM 自主决定"要不要维护状态"这件事本身就是 goink 用三重保障硬堵的坑），不建议引入；固定流水线+确定性闸门更适合本框架"批量+可控"的定位。
4. **独立审稿 Agent 做语义级一致性比对**（而非只靠确定性规则）—— 有潜力，但应该是"锦上添花"的第二意见，不应替代现有确定性闸门，可作为后续方向。

## 四、POC：真语义嵌入 vs 现有哈希词袋检索

### 4.1 问题实锤

用一对"同一事实的不同措辞"（复述）和一句无关句子，分别用现有 `build_hashed_embedding`（`retrieval.py`）和真语义模型算相似度：

```
已建立事实：他左眼失明，是十年前那场大火留下的伤
复述改写：  他的左眼看不见东西，因为很多年前被烧伤过
无关句子：  她今天穿了一件红色的连衣裙去赴宴
```

| 方法 | 复述 vs 已建立事实 | 无关句 vs 已建立事实 |
|---|---|---|
| 现有哈希词袋（`build_hashed_embedding`） | **0.139** | 0.183（**反而更高**） |
| 真语义嵌入（`paraphrase-multilingual-MiniLM-L12-v2`） | **0.852** | 0.077 |

现有哈希词袋方法不仅信号弱，而且**方向是错的**——复述同一事实的句子比不相关的句子分数更低。这意味着如果检索用它来判断"这件事是否已经建立过"（例如反重复设定、伏笔回收匹配、canon fact 冲突检测），只要写手换一种措辞，命中率就会显著下降，甚至被无关内容抢占 top-k。

### 4.2 落地的最小改动

新增 `src/bestseller/services/semantic_embedding.py`：

- `build_semantic_embedding(text) -> list[float] | None`：与 `retrieval.cosine_similarity` 同构（同样是归一化向量、同样的调用形状），可直接替换或并行于 `build_hashed_embedding` 使用。
- 依赖 `sentence-transformers`（`pyproject.toml` 中 `bestseller[embeddings]` extra **早已声明但从未被实际调用** —— 说明这条路径本就是预留的，只是没接上）。
- 优雅降级：包/模型不可用时返回 `None`，调用方可回退到哈希词袋，不会破坏离线/无网络环境。

新增测试 `tests/unit/test_semantic_embedding.py`，3 个用例全部通过，用真实数据复现了上表的差距（含一个专门记录"哈希词袋会把复述排在无关句子之后"这一失效模式的回归测试）。

### 4.3 尚未做（有意保留给后续决策）

- 未修改 `retrieval.py` 的生产调用路径或 `RetrievalChunkModel.embedding` 的写入逻辑——真接入需要决定：全量切换 embedding 后端，还是双跑（哈希做快速粗筛 + 语义做精排/复核）,以及模型下载/缓存策略（离线部署环境的模型分发）、embedding 维度变化对已有索引的迁移成本。
- 未接入具体质量闸门（如 `world_law_consistency_gate.py`、`payoff_ledger_gate.py`）做"语义级已建立事实冲突检测"，这是最有价值的下一步，但涉及闸门行为变更，需要专门验证不引入误判。

## 五、建议的下一步（如果决定推进）

1. 在 `AppSettings.retrieval` 加一个 `embedding_backend: Literal["hashed", "semantic"]` 开关，默认 `hashed`（不改变现有行为）。
2. 语义嵌入维度（384）与现有哈希嵌入维度（`AppSettings.retrieval` 里配置的 dimensions）不同，`RetrievalChunkModel.embedding` 需要按后端分列存储或重建索引，不能混用。
3. 先在 `canon_guardrails.py` 或 `payoff_ledger_gate.py` 这类"复述改写就该命中"的场景做小流量 A/B，而不是一次性全量切换。
