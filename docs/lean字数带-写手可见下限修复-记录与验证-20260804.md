# lean 字数带：写手可见下限修复 — 记录与验证（2026-08-04）

## 1. 诊断（代码证据）

**症状**：lean profile（生产默认，`config/default.yaml` `pipeline.prose_prompt_profile: lean`）下写手稳定欠产 ~21%：11 稿 0 达标、第 1 章五次全聚在 2000±70（见记忆库「写手稳定欠产21%字数」）。最新 lean 书《欠我者，寿来偿》（custom-xuanhuan-1785814121）32 稿中 7 稿低于 1800 硬下限，大量聚在 1900–2000。

**根因**：门禁在验一个模型根本看不见的下限。lean profile 同时砍掉了两处字数信号：

| 被砍块 | 位置 | 砍法 |
| --- | --- | --- |
| 【字数与结构】整块（289 字，含下限/目标/上限） | `drafts.build_chapter_first_draft_prompts` 注入位 | `LEAN_DROPPED_SECTIONS` 含 `word_count_rules`（注释称 "length_stability_gate owns this"） |
| 章节体量门块（`chapter_length_block`） | 【硬约束与门禁】子字段 | `LEAN_DROPPED_CONSTRAINT_FIELDS` 含 `chapter_length_block` |

结果整个 prompt 里唯一的数字是【删减策略】里的 3500 上限——下限 1800、目标 2600 完全不可见，而 `length_stability_gate` 照常验 1800 下限。`llm_runs.metadata.protected_contract_markers.word_count`（检查 prompt 是否含「字数与结构」）在 lean 下恒为 False，铁证。

**复现**：lean 渲染 chapter_first_writer prompt，全文 0 次出现 1800、0 次出现 2600、1 次出现 3500（仅删减策略）。真书（上述书第 7 章）真机路径渲染同样成立。

「gate owns this」的前提错误在于：门禁只能拒稿，不能让模型知道往哪写。验收权在门禁没错，但**契约数字必须对生成方可见**。

## 2. 修复

原则：不恢复 289 字大块（剂量-响应实验证明过量指令有害），只补一行极简字数带，数字与门禁同源。

- `drafts.build_chapter_first_draft_prompts`：lean 下在原 `word_count_rules` 注入位换成一句话——
  `【字数与结构】\n本章正文 {hard_min}-{hard_max} 个汉字，目标约 {hard_target} 字。`（+40 字符）
  数字来自同函数内既有的 `_chapter_length_contract_band(project, target_word_count)` 调用——与 `length_stability_gate` 同一带宽来源，单一真源。英文书对应一行 `[word count and structure]`。
- 沿用「字数与结构」块名，三处消费者零改动归位：
  1. `protected_contract_markers.word_count`（llm_runs 元数据）lean 下恢复 True；
  2. compiled 模式 section 命名映射到 `word_count_rules`（prompt manifest 必需节达成）；
  3. soft-trim 必保尾部锚点（`_MUST_KEEP_TAIL_MARKERS_*`）保护该行不被截断。
- `prose_prompt_profile.LEAN_DROPPED_SECTIONS` 注释更新为实况（lean 换极简带行，非裸删）。
- full profile 字节不变（无行为回归）。
- 场景路径（非 chapter-first）不受影响：其 `_scene_word_budget_line` 本就不走 profile 门控，lean 下仍在——真空只存在于 chapter-first 路径。

## 3. 三层验证

**L1 单测**（`tests/unit/test_prose_prompt_profile.py::TestLeanKeepsTheWordBand`，4 断言）：
- lean prompt 含与 `_chapter_length_contract_band` 同源计算的「本章正文 {min}-{max} 个汉字，目标约 {target} 字。」（测试内重算带宽，不写死数字）；
- 块名喂 protected marker；
- 289 字大块仍被砍（「字数是硬交付」「发布硬范围」不出现）；
- no-op：full profile 不新增带行、大块仍在。
- 原「lean 砍掉【字数与结构】」断言改为断言大块特征文本（块名现由带行合法持有）。
- 结果：文件 42 passed。

**L2 回归**：10 个 prompt 相关测试文件 141 passed。全量 tests/unit：12 failed / 8930 passed——git stash 干净树归因：同选集干净树同样 6 failed（distilled_strategy / framework_self_closure / legacy_bootstrap / methodology_gate / web preset，均与本改动无关），另 6 个（workflow_services 5 + outline_materialization 1）为全量语境顺序依赖失败、隔离运行两种树均过。**0 个本次引入**。

**L3 真机 + A/B**（同章多稿，改参数前先跑 A/B 的既定纪律）：
- 接线证明（零 token）：生产库真书《欠我者，寿来偿》第 7 章走完整 runtime 路径（`build_chapter_writer_context` → `_enrich_chapter_first_context` → `build_chapter_first_draft_prompts`，SELECT-only + rollback），两臂 prompt diff 恰好只有那 40 字符字数带。
- 真机 A/B：MiniMax-M3、生产 writer 参数（temp 0.85、runaway max_tokens 同产线公式）、A 臂=修复前（去带行）、B 臂=修复后，各 6 稿，交错并发，直连 litellm 零 DB 副作用。字数用门禁同一把尺（`count_zh_chars` on sanitize 后正文）。

**A/B 结果（两轮合并，同章交错采样；空稿为收割怪癖、两臂对称各失 1-2 稿，已剔除）**：

| 指标 | A 臂·无字数带（修复前） | B 臂·有字数带（修复后） |
| --- | --- | --- |
| 有效稿数 | 11 | 10 |
| 分布 | 1244–3414（极差 2170，std 679） | 1513–2182（极差 669，std 241） |
| mean / median | 2090 / 1962 | 1897 / 1901 |
| 破下限（<1800） | 4/11，平均差 335 字（最深 -556） | 4/10，平均差 147 字（最深 -287） |
| 深度欠产（<1600） | 3/11 | 1/10 |
| 超上限（>3500） | 0（但有 3414 险稿） | 0（最高 2182） |

**判读（诚实版）**：
1. **不引发超上限**：干净达标。B 臂最高 2182，离 3500 很远；反而是 A 臂无锚时会飙到 3414。
2. **欠产改善 = 部分成立**：字数带消灭的是「无锚噪声」——方差坍缩 ~2.8 倍、深度欠产稿（1244/1378/1518 这种必然触发多轮修复踩踏的废稿）基本消失、破限稿从「差 300-556 字」变成「差 11-287 字」（修复循环从多轮踩踏变一轮小补）。
3. **但破限率没降、mean 反而略低**：带行可见后模型把「目标约 2600」稳定实现成 ~73%（中位 1901，**10 稿没有一稿到过 2600**），收敛点压在下限正上方。可见性修复了「看不见」，没有修复「实现率折损」——后者正是 `word_targets._PRODUCTION_FLOOR_REALIZATION` 已建模的现象，属 `chapter_first_writer_aim` 补偿轴，不是再加 prompt 块能治的。

**Arm C（补偿轴穿透验证）**：显示 aim 抬到 3200（模拟生产已有 per-book 旋钮 `metadata["chapter_first_writer_aim"]=3200`，门禁带宽 1800-3500 不动，带行显示「目标约 3200」）：

| 指标 | C 臂·带行 + 显示目标 3200 |
| --- | --- |
| 有效稿数 | 5（1 空稿收割怪癖） |
| 分布 | 1377 / 2885 / 3921 / 6095 / **8751**（std 2883） |
| 破下限 / 带内 / 超上限 | 1 / **1** / **3**（最高为上限的 2.5 倍） |

**C 臂被强证据证伪**：把可见目标从真实 2600 抬到补偿位 3200，不是把分布温和上移，而是**炸掉锚定纪律**——3/5 超上限（3921/6095/8751）、方差从 241 爆到 2883、带内率从 6/10 跌到 1/5。解释：显示「目标约 2600」时模型的成稿计划就是「一章正常戏」（其自然长度 ~2000，被带行拉着收敛）；显示 3200 会诱使它加戏填量，一旦脱离自然长度，上限约束也随之失灵（runaway guard 本就不是长度控制器，8751 字照放行）。**结论：不要把 `chapter_first_writer_aim` 抬到 3200 之类的补偿位——该轴穿过可见带行时是负杠杆。** 这也解释了 ground truth 里 6906 字野稿的来源形态。

## 4. 最终裁决与残留

**裁决：ship B 臂（本修复），拒绝 C 臂。**
- B 严格优于 A：方差 ↓2.8×、深度欠产稿 3→1、破限深度 335→147 字（修复循环从多轮踩踏变一轮小补）、近上限险稿 1→0、`protected_contract_markers.word_count` 归位。超上限零发生。
- B 的残留缺口（~40% 稿差下限 ≤300 字、无稿到 2600）是**模型实现率属性**（M3 实现 ~73% 的声称目标），不是 prompt 可见性问题；且 C 臂证明「抬高可见目标」是负杠杆。残留由既有修复路径消化（`_chapter_auto_repair_length_contract` 带完整字数契约，补 147 字均差是一轮量级）。
- 若将来要治实现率，方向是**不经过可见带行**的轴（如按实现率缩带宽的门禁侧策略或换模型），任何动作先过本文同款同章 A/B。

**影响面**：只动 chapter-first 写手 prompt 的 lean 分支；full（字节不变）、场景路径（`_scene_word_budget_line` 本就不走 profile 门控）、门禁、修复路径均不变。

**测量注**：A/B 采样为直连 litellm 的收割怪癖会产生零星空稿（chars_raw=2，三轮共 4 个、臂间对称），生产 `complete_text` 有兜底重试不受影响；空稿已从统计剔除。
