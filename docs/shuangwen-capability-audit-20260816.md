# 爽文能力审计：为什么三本书全是「零爽点结算」（2026-08-16）

> 触发：用户要求建立爽文方法论与评测体系。
> 动手之前先做家底审计——结果发现要建的不是"一个评测器"，而是"整条断掉的链"。
> 本文只记**已实证**的事实，每条注明证据来源。

---

## 一、结论摘要

**爽感这条线从配置 → 生成 → 落库 → 验收，整条是断的。**
不是模型不会写爽点，是没人告诉它写、没人检查它写没写。

框架里有一整套爽感引擎（12 类爽点分类、7 段密度曲线、配方系统、强度评分器），
但在真实生产路径上**一条数据都没产出过**。

---

## 二、根因链（逐环实证）

| 环 | 事实 | 证据 |
|---|---|---|
| 1 | `hype_scheme_from_preset_overrides` 给对入参**工作正常** | 传 `{"hype":{"recipe_deck":_MALE_POWER_HYPE_DECK}}` → deck=5, is_empty=False |
| 2 | 我们的书 **`writing_profile_overrides` 根本不存在** | 三本书 projects.metadata 无此键 |
| 3 | → `is_empty=True` | 空入参实测 |
| 4 | → `build_chapter_hype_blocks` 立即返回 `EMPTY_HYPE_BLOCKS` | `prompt_constructor.py:1192-1193` |
| 5 | → 爽点约束整块**不进 prompt** | 同上 |
| 6 | → hype 三字段从未赋值 | **三本书 109 章 `hype_type`/`hype_intensity`/`hype_recipe_key` 100% NULL** |
| 7 | → 正文零爽点结算 | 两把独立尺子互证（见下） |
| 8 | → 三个门禁全 `audit_only` 不报警 | `quality_gates.yaml:250-254` |

**为什么没有 `writing_profile_overrides`**：我们的书走 **taxonomy 选择路径**
（频道·题材·子题材），而爽点配置只挂在**旧 preset 路径**上。这是
「目录↔taxonomy 两套词汇表」老病的新形态。

## 三、正文实测：爽点覆盖率

| 书 | 现成分类器（玄幻词表） | 市井/喜剧词表复测 |
|---|---|---|
| 《端盘画神》50 章 | **零爽点 36/50（72%）** | — |
| 《破澡堂真话局》50 章 | 零爽点 **50/50（100%）** | **49/50**（唯一命中是「跪了一夜」的悲情回忆，误报）|

两把独立的尺子结论一致 → **不是仪器盲区，是书里真的没有**。

对照平台口径：`config/platform_profiles.yaml:231` 番茄「每章必须 ≥1 个明确爽点」。
我们 28% vs 目标 100%。

⚠️ 但现成分类器**确实题材盲**：`_HYPE_KEYWORDS_ZH` 94 个词重度玄幻偏向
（突破/晋阶/真身/神识/金光/碾压/吊打/镇压），市井喜剧的爽点形态
（免债/认输/改口/道歉/当众社死）**一个都不在表里**。新体系的词表必须跨题材。

## 四、结构性缺陷：爽感的位置放错了

爽感被当成**某些题材的属性**，而不是**正交的轴**。

- 31 个 prompt pack 里只有 20 个有 `payoff_rhythm`，
  而**玄幻升级、都市逆袭这两个最该有爽点节奏的包反而没有**
- 只有 1 个包（paranormal-romance）有结构化 `hype` 键
- 喜剧包 `shezhu-bailan-comedy` 的 payoff_rhythm 是
  「每章 3 个笑点 + 1 个微小治愈时刻」——**这是治愈系，不是爽文**

后果：想建「爽文喜剧」时，`comedy-absurd` 子题材路由到治愈包，
拿到的是治愈指令。**那本书是忠实执行了自己拿到的指令**，问题在选择层。

**正确模型**：爽文 = 题材 × 爽度档位。同一玄幻可写成爽文或正剧；
同一喜剧可以是爽文喜剧（打脸解气）或治愈喜剧。现在系统里没有这个轴。

## 六、读者盲评给出的通用律（三类爽文读者独立评估后的唯一共识）

> **「赢」必须①落到一个具体的人脸上 ②被具体的人看见 ③在主角账上留下一笔能带走的东西。**

三件缺一件，文笔再好都是「这章不爽」。三条都可拆成可判定检查：

| 通用律 | 可测形态 |
|---|---|
| 落到具体的人 | 有名字的对手，且本章之前具体得罪过主角 |
| 被具体的人看见 | 证人的称呼/动作/待遇发生具体变化——「众人震惊」不算 |
| 账上留一笔 | 章末主角多了一样能说出名字、下一章还能用的东西 |

**分歧同样有用**——证明爽是分频道的，评测必须分档：

| | A 番茄免费男频 | B 起点付费老书虫 | C 女频 |
|---|---|---|---|
| 爽的形态 | 物理碾压+当众羞辱 | 规则自洽+格局位移 | 被认可+掌控场面 |
| 憋屈耐受 | 1–1.5 章 | 3–5 章 | 2 章 |
| 反派智商 | 可以低 | **必须高** | 坏得聪明且长记性 |
| 整章不爽 | 需钩子替代 | 接受布局章（要信息增量）| 需温情替代 |
| 对手下场 | 挨打出丑 | 可放走，格局赢即可 | **必须实际损失，原谅=不爽** |

同一段文字在三档下评分可能完全相反（主角一句话不说赢了：C 高分、A 低分）。

## 七、既有可复用资产（不要重造）

1. `HypeType` 12 类分类法（6 处在用）——新体系必须复用同一枚举
2. `HYPE_DENSITY_CURVE` 密度曲线（已与 pacing BEAT_SHEET 对齐）
3. `build_hype_constraints` prompt 渲染器——唯一让爽点进 LLM 的口子
4. `reader_judge.payoff_density`（权重 0.22，判据成熟）+ 影子校准脚本，**默认关闭**
5. `config/hook_pull_eval.yaml` 正/负/对照样本集范式 → 直接照抄成 `shuangwen_eval.yaml`
6. `config/rejection_repair_playbook.yaml:157-186 weak_satisfaction` 现成修复剧本
7. `config/chapter_position_profiles.yaml:140` 的 0/0.5/1 可感度分级尺
8. `.distillation_private/` 人类语料 + `ai_flavor` 检测器架构范式

## 八、方案方向（五层，缺一层都会回到"造了尺子量一个从不生产的东西"）

1. **配置层**：爽点配方 YAML 化，taxonomy 子题材可取；新增「爽度档位」正交轴
2. **生成层**：约束真的进 prompt（现被 `is_empty` 短路）
3. **落库层**：hype 字段真的写进 DB（现 100% NULL，任何基于它的评测都空转）
4. **评测层**：确定性检测器 + LLM 判官，**词表必须跨题材**，分三档尺子
5. **验收层**：门禁从纸老虎改为能触发重写（**仍不给杀权**）

**本轮验收标准**：真机 DB 里必须看到 hype 记录落库、正文爽点覆盖率达标——
不是单测绿就算完。（教训来源：本项目反复出现"检测器造了没接线"。）
