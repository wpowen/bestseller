## 一、爽文是什么：一条通用律 + 三档分尺

### 1.1 通用律（三档读者独立评估后的唯一共识）

> **「赢」必须①落到一个具体的人脸上 ②被具体的人看见 ③在主角账上留下一笔能带走的东西。**

三件缺任何一件，文笔再好都会被判"这章不爽"。三条都可拆成可判定检查：

| 通用律 | 判据 | 反例（读者原话） |
|---|---|---|
| 落到具体的人 | 有名字的对手，且**本章之前**具体得罪/轻视/阻挠过主角 | "'某个势力'不算" |
| 被具体的人看见 | 至少一个证人的**称呼/动作/待遇**发生具体变化 | "「众人震惊」四个字不算变化" |
| 账上留一笔 | 章末主角多了一样**能说出名字、下一章还能用**的东西 | "爽了三秒，账上是零" |

### 1.2 爽 ≠ 题材，爽是正交轴

**这是本方法论最重要的结构主张。**

现状：爽感被当成某些题材的属性——31 个 prompt pack 里 20 个有 `payoff_rhythm`，
而**玄幻升级、都市逆袭这两个最该有的反而没有**；喜剧包给的是
「每章 3 个笑点 + 1 个微小治愈时刻」（治愈系，不是爽文）。

正确模型：**爽文 = 题材 × 爽度档位**。同一玄幻可写成爽文或正剧；
同一喜剧可以是爽文喜剧（打脸解气）或治愈喜剧。用户想要"爽文喜剧"时，
系统里必须有这条路，而不是只能选到治愈包。

### 1.3 三档分尺（同一段文字在不同档下评分可能相反）

| | **A 即时碾压**（番茄免费男频） | **B 规则智斗**（起点付费） | **C 关系认可**（女频） |
|---|---|---|---|
| 爽的形态 | 物理碾压 + 当众羞辱 | 规则自洽 + 格局位移 | 被认可 + 掌控场面 |
| 憋屈耐受 | 1–1.5 章 | 3–5 章 | 2 章（且须已在还手）|
| 铺垫:爽 | 3:7 | 5:5 ~ 4:6 | 4:6，且要分散给 |
| 反派智商 | 可以低 | **必须高**，输在合理误判 | 坏得聪明且长记性 |
| 整章不爽 | 需钩子/小爽替代 | **接受布局章**（须有信息增量）| 需日常温情替代 |
| 金手指规则 | 几乎不在意 | **最严**，新增设定即退订 | 在意"能力是否真属于她" |
| 对手下场 | 挨打、出丑 | 可放走，格局赢即可 | **必须实际损失，原谅=不爽** |
| 观众 | 越公开越好 | 不在意人数，在意势力判断 | 熟人在场，须含利益相关者 |
| 失败的价值 | 减分（除非换到东西）| **加分**（暴露误判并改进）| 中性偏加（证明选择的重量）|
| "安静地赢" | 不喜欢 | 喜欢 | **最喜欢** |

典型冲突：主角一句话不说赢了 → C 打高分、A 打低分。
**因此任何单一尺子都是错的。**

### 1.4 代价与爽感的关系（澄清一个常见误解）

三档一致：**代价在满足两个条件时增强爽感**——
①主角**知情下主动选择** ②**具体可量化**且**后续被记住**。
凭空倒霉、被设定坑、为"显得不无脑"而安排的失败，三档一致减分。

> B 档原话："没有代价的爽是塑料的。"
> A 档原话："我不是来看他倒霉的。"

## 二、被真机数据证伪的假设（不许再用）

语料量化（2114 本，含长度配平与逐句精度核验）推翻了三条直觉：

| 假设 | 实测 | 结论 |
|---|---|---|
| 爽文对话更多 | **AUC 0.501**，两组中位都 0.22–0.25 | **零区分力**。对话饥饿是可读性问题，与爽文无关 |
| 「结算词密度」能测爽 | A vs C **AUC 0.52**；A vs B **反向** | 它测的是"有没有冲突和道歉"，**文学小说反而更多** |
| 敬称密度能测地位翻转 | AUC 0.538 | 测的是**译制腔**（Mr.→先生）|
| 前蔑称→后敬称位置代理 | **反向**（A 0.05 < B 0.125）| 无效 |

**另一条重要警告**：人工挑选的高分网文，碾压密度**低于**普通爽文
（精修碾压 0.017 vs 0.036）。**碾压密度是"爽文属性"的标记，不是"质量"的标记**——
不可当作越高越好的优化目标。

## 三、可测性分层（每条特征标注归属）

### 3.1 确定性层：只能做**告警带**，不能做硬闸

最强单指标 AUC 仅 **0.716**，且词表实测误报率高（结算词 40%、碾压词 45%）。
因此确定性层的定位是"超出人类分位数就提示"，不是"判定爽不爽"。

| 指标 | 人类基线（含该特征的**章占比**）| 我们两本书 | 用途 |
|---|---|---|---|
| **碾压·不对称**（AUC 0.704，最强）| p10 0.09 / 中位 **0.37** / p90 0.68 | **0.02 / 0.00** | 主告警 |
| 碾压（全词表）| p10 0.11 / 中位 0.42 / p90 0.78 | 0.20 / 0.10 | 辅助 |
| 结算（精修）| p10 0.03 / 中位 0.15 / p90 0.45 | 0.06 / 0.04 | 辅助 |
| 碾压副词（直接/当场/瞬间）| 中位 0.254/千字 / p90 1.031 | — | 辅助 |
| 单句独段占比 | 中位 0.500 / p90 0.845 | — | 节奏参考 |

> **我们的位置**：在唯一真正区分爽文的指标上，两本书都在**人类 p10 以下**。
> 注意这个人类基线**包含大量文学小说与译作**——我们不是"不够爽"，
> 是比普通小说还低一个数量级。《破澡堂真话局》不对称碾压覆盖率 **0.00**（50 章零次）。

### 3.2 LLM 判官层：爽文的核心判断在这里

以下 7 件事**文本层测不出来**，正则永远解决不了：

1. **「解气」本身**——读者情绪兑现无文本代理
2. **极性归属**——「不是对手」是谁不是谁的对手（需施事者识别）
3. **否定与反问**——「没来道歉的意思」「何必认罪呢」在词表眼里与真道歉相同
4. **称谓翻转**——需指代消解 + 说话人归属
5. **铺垫是否等价兑现**——跨段落因果，词表零信号
6. **爽点是不是"挣来的"**——靠金手指白给 vs 靠布局，表面同形
7. **跪拜/情感道歉 vs 屈服**——语义角色差异

### 3.3 不可测（只能靠人）

- 特定读者群的口味漂移
- 同一爽点在不同文化语境下的接受度

## 四、评测体系设计

### 4.1 三层结构

```
① 确定性告警带（零 LLM 成本，<100ms）
   碾压不对称覆盖率 / 结算覆盖率 / 副词密度 / 单句独段
   → 低于人类 p10 或高于 p90 时发 warn，进 deslop 触发集
   → 绝不阻断（AUC 0.72 不配拥有杀权）

② LLM 爽点判官（章级，分三档尺子）
   输入：章正文 + 档位(A/B/C) + 前情摘要
   输出：通用律三问的是/否 + 分档追加问 + 一句定性
   → 判据来自读者盲评的 37 条检查表
   → warn/重写，不阻断

③ 书级爽点曲线（跨章）
   覆盖率、连续无爽点章数（分档硬线：A≤1 / B≤3 / C≤2）
   铺垫:结算 比例是否匹配档位
```

### 4.2 铁律（都是本项目付过学费的）

1. **只挣重生和留痕，无杀权**——新检测器不得产生 `blocks_write`
2. **prompt 不种词**——只给类别与正向方向，token 只留检测器层。
   爽文尤其危险：把"打脸/跪下/求饶"写进 prompt，所有书会长成同一副样子
3. **词表必须跨题材**——现成分类器 94 个词重度玄幻偏向，
   市井喜剧的爽点（免债/认输/改口/当众社死）一个都不在表里
4. **先证伪现有机制再动手**——本项目反复出现"同一事实住两个地方"
5. **验收看真机 DB**，不是单测绿

### 4.3 与现有资产的关系（不要重造）

| 复用 | 说明 |
|---|---|
| `HypeType` 12 类分类法 | 必须复用同一枚举，否则又是两套词汇表 |
| `HYPE_DENSITY_CURVE` | 已与 pacing BEAT_SHEET 对齐 |
| `build_hype_constraints` | 唯一让爽点进 LLM 的口子 |
| `config/hook_pull_eval.yaml` 范式 | 直接照抄成 `shuangwen_eval.yaml`（正/负/对照 + 验收线）|

| 需先修 | 说明 |

## 五、验收标准（不达标就回炉）

| # | 标准 | 判据 |
|---|---|---|
| 1 | **人类爽文语料判高分、文学语料判低分** | A 组 vs B 组判官分中位差 ≥2（10 分制）|
| 2 | **判官与读者盲评一致** | 我们两本真书的判官分排序须与读者/作家盲评一致 |
| 3 | **误报可控** | 人类语料误报率 <5% |
| 4 | **真机落库** | 新书 DB 里 `hype_type`/`hype_intensity` 不再是 NULL |
| 5 | **正文可见改善** | 新书不对称碾压覆盖率 ≥ 人类 p10（0.09），目标向中位 0.37 靠 |
| 6 | **不误伤非爽文书** | 治愈/正剧书不因低碾压被判失败 |
| 7 | **零杀权** | 全流程无 `blocks_write` |
