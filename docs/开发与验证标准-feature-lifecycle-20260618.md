# 开发与验证标准 · Feature Lifecycle

> 立项：2026-06-18　|　适用范围：本仓库（Mode A 系统开发）的一切功能开发、修复、增强
> 范本：《[故事增强 → 正文层接线 · 记录与验证](story-enhancer-prose-wiring-记录与验证-20260618.md)》
> **本标准是强约束：后续所有功能开发、验证与文档记录，一律按此执行。**

---

## 0. 为什么要这个标准

历史教训反复出现两类坑：
1. **「测量假象」误判**——质量门读错字段、报 0% 命中，差点据此把已生效的功能重做。
2. **「结构达标 ≠ 真生效」**——大纲 / schema 通过了，但数据在交接链上断掉，正文 / 成品并未兑现。

根治办法：诊断走完整链路、验证必须跑到「真机端到端」、并把每次结论沉淀成可复查的文档。本标准把这条纪律固化。

---

## 1. 五个阶段（每个功能都要走完）

### 阶段 0 · 诊断（先证据，后动手）
- 用**代码证据（`file:line`）走完整链路**定位根因，禁止凭猜测下结论。
- 显式区分两种失败：**测量假象**（门 / 审计读错字段）vs **真断点**（数据真没传到）。
- 链路要走到底：生产 → 持久化 → 物化 / 装配 → 消费端 prompt。任一环节都可能丢字段。
- 判断「消费端是否真拿到」的硬手段：**grep 消费端（如写手 prompt builder）里的字段名**，0 命中即断点。

### 阶段 1 · 计划
- **soft / additive 优先**：能加注入 / 软建议解决的，绝不加硬闸门。
- **禁自伤硬闸门**：不得让一个 gate 因模型没填某字段就 `raise` 拍死整卷 / 整本。
- **未启用时字节级不变**：新增能力在「未勾选 / 无数据」时必须产出与历史完全一致的结果。
- **单一真源**：消费端复用既有渲染器 / 合同，避免与生产端漂移。
- **输入封顶**：注入 prompt 的内容必须截断 / 限量，防止撑爆上下文预算。

### 阶段 2 · 实现
- 小而聚焦的 diff；镜像既有写法（如新增字段持久化就照抄相邻字段的 truthy→set / else→pop 范式）。
- 多小文件优于大文件；纯新增优于改写既有逻辑。

### 阶段 3 · 验证（**强制三层，缺一不可**）

**L1 单元测试**
- 覆盖正常 / 边界 / 异常分支。
- 必含 **no-op / 字节级不变断言**（证明「未启用时无副作用」）。

**L2 回归**
- 跑所有相关测试（消费端 + 生产端 + 集成）。
- **任何失败必须 `git stash` 在干净树复跑归因**，明确区分「本次引入」与「既有失败」，并在文档写明。

**L3 真机端到端（最关键，不可省）**
- 在 **live docker 栈**（`docker compose` 的 db / redis / worker）上驱动**真实运行时路径**，而非 SimpleNamespace 模拟。
- **零 token**：把 LLM 调用（如 `complete_text`）全模块打桩，返回 `fallback_response`。
- **零副作用**：
  - 用 `BaseException` 哨兵在目标函数（如 `build_scene_draft_prompts`）后截获产物并中止——`BaseException` 不被 `except Exception` 吞、`session_scope` 只在 clean exit 时 commit，故自动跳过提交。
  - 结束**核验数据源未被污染**（直接查 DB）。
- **产出"携带性 / 能力"对比证据**：before/after 或 variant A/B 的结构化对照表（命中了什么、缺什么）。
- 范本脚本：`scripts/verify_story_enhancer_prose_e2e.py`（可直接照搬这套「打桩 + 哨兵 + 不 commit + 对比表」骨架）。

### 阶段 4 · 文档记录（见 §2）
- 写一份 **功能特性记录 + 验证报告**（合一）入 `docs/`，并登记到 README 文档索引。

### 阶段 5 · 提交
- **验证全绿后才提交**。
- 遵循 conventional commits（`feat / fix / test / refactor / docs / chore …`）。
- **本仓约定不带 `Co-Authored-By` 尾注**（与历史一致）。
- 功能改动与无关改动分到不同 commit；提交体写清根因、改动、验证结论。

## 2. 文档记录规范

### 2.1 命名约定（`docs/` 根目录）
| 文档类型 | 命名 | 何时写 |
|:--|:--|:--|
| 开发方案 / 计划 | `<feature>-development-plan-<YYYYMMDD>.md` 或 `<特性>-开发计划-<日期>.md` | 立项 / 设计阶段 |
| 功能记录 + 验证报告（合一） | `<feature>-记录与验证-<YYYYMMDD>.md` | 功能完成且验证通过后 |
| 验证报告（独立） | `<feature>-verification-report-<YYYYMMDD>.md` | 需要单独留存真机验证证据时 |
| 实现复盘 | `<特性>-实现复盘-<日期>.md` | 发现实现与设计偏差时 |

小功能可只写一份「记录与验证」合一文档；大功能可拆「开发计划 → 验证报告 → 复盘」三件套。

### 2.2 功能记录文档模板
```
# <功能名> · 功能特性记录与验证报告
> 日期 | 分支 | 提交哈希 | 关联能力 | 遵循本标准

0. TL;DR（一句话结论）
1. 背景与根因（用户症状 + file:line 证据表）
2. 设计与落地（设计原则 + 改动清单表 + 运行时数据流）
3. 验证（L1 单测 / L2 回归含归因 / L3 真机端到端含对比表 + 零副作用证明 + 复跑命令）
4. 结果与结论
5. 提交记录
6. 一句话总评（沉淀可迁移的教训）
```

### 2.3 索引维护
- 重要文档（标准、核心功能记录）必须加进根 `README.md` 的 `## 文档索引` 表。
- agent 开发指南 `.claude/skills/bestseller-framework/SKILL.md` 的 Mode A 表里，应能指向本标准。

## 3. 验收 Checklist（提交前自检）

- [ ] 阶段 0：根因有 `file:line` 证据，链路走到消费端
- [ ] 阶段 1：soft/additive；未启用字节级不变；单一真源；输入封顶
- [ ] L1：单测含 no-op 断言，全绿
- [ ] L2：相关回归全跑；失败已 `git stash` 归因
- [ ] L3：live 栈真机端到端跑通；零 token；零副作用（DB 已核验未污染）；有 before/after 对比证据
- [ ] 阶段 4：`docs/` 有记录文档；README 文档索引已登记
- [ ] 阶段 5：conventional commit；无 `Co-Authored-By`；功能与无关改动分离

---

## 4. 一句话总纲
**先证据后动手、能软不硬、未启用零变化、验证必到真机端到端、每次都留可复查的文档。**
