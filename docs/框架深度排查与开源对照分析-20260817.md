## 1. 三问总判

### Q1. 当前框架到底有什么问题？

**结论（High）**：架构上已经是多题材平台（taxonomy + 31 pack + contamination guard）。排查当时横切默认会把未选手台的书拉进「番茄短回报 × 七猫开篇合同 × 爽文融合」；**§0.2 晚间已改为 opt-in**。账单 / 死亡 / 尸体系列不进 writer prompt。

### Q2. 是否正常运行？

**结论（High）**：基础设施能跑。2026-08-17 本机 Docker 8 服务 healthy，API `/health` ok，Web 8787 返回 200，LLM `mock=false`，ARQ 队列为空。当前没有活跃生成任务。不能当成「无人值守可持续跑完长书」：已完成书出现 self_heal `ABANDONED`，门禁预算耗尽会转人工。

### Q3. 能否持续输出高质量并闭环？

**结论（High）**：结构闭环已接线（WRITE → REVIEW → REWRITE≤2 → EXTRACT → 下一章；Mode B 走同一 `run_chapter_pipeline`）。读感闭环是半套：默认 `quality_mode=closure` 记债放行；persona 阈值高于写手天花板后软熔断；reader-judge 影子模式不改分；两本 50 章书都在后半段劣化。

## 3. BestSeller 自身设计（对照用地图）

### 3.1 分层

```
HTTP Client / Web UI :8787
    → FastAPI :8000
    → ARQ Worker ← Redis → APScheduler
    → services/pipelines.py
    → planner / drafts / reviews / knowledge / context / retrieval / continuity
    → PostgreSQL 16 + pgvector    Redis
```

**事实源纪律（证据）**：运行时事实在 PostgreSQL。`progress.yaml` 是带 `workflow_run_id` 的文件编排投影，不是权威源。Mode B 若只读 yaml、不读 DB，会和主流水线脱节。

核对：`.cursor/rules/bestseller-orchestrator.mdc` §5；`src/bestseller/services/mode_b_bridge.py` `sync_progress_yaml`。

### 3.2 角色与温度

| role | 用途 | 配置入口 |
|------|------|----------|
| planner | 规划 | `src/bestseller/settings.py` LLM role map |
| writer | 正文 | 同上 |
| critic | 评分 | 同上 |
| summarizer | 知识压缩 | 同上 |
| editor | 定点重写 | 同上 |

硬约束：所有 LLM 必须经 `src/bestseller/services/llm.py::complete_text`，必传 `project_id` + `workflow_run_id`。

### 3.3 章节流水线（实际顺序，chapter-first 主路径）

对照 `src/bestseller/services/pipelines.py` 中 `run_chapter_pipeline` 附近：

1. 写场景 / 整章装配
2. stamp chapter hype
3. persona grade + reader_judge（影子）
4. retention_safety_gate
5. chapter auto-repair 循环
6. ai_flavor_gate（可 block）
7. review_chapter_draft + rewrite 循环
8. promote 成功才 `extract_chapter_state_snapshot`
9. export markdown

**推断**：EXTRACT 不在 review 失败且未 promote 的路径上。失败章若被 closure 记债放行，后续章仍可能读到低质量前文。

### 3.4 双模式

| 模式 | 入口 | 与主流水线 |
|------|------|------------|
| Mode A | Web / API / ARQ `run_project_pipeline_task` | 主路径 |
| Mode B | Cursor orchestrator → `scripts/mode_b_chapter_bridge.py` → `mode_b_bridge.drive_mode_b_chapter` | 已调用 `run_chapter_pipeline`；pass 三合取：`not requires_human_review and final_verdict == "pass" and not block_codes` |

核对：`src/bestseller/services/mode_b_bridge.py` 约 676–680 行 `passed =`。

### 4.4 行业共识（与 2026-07-11 文档一致，本轮仍成立）

1. 骨架都是规划 → 逐章写 → 审 → 回写状态。差异在事实源和停机纪律，不在「有没有角色分工」。
2. 全行业几乎拿不出「质量好」的公开成书证据。autonovel 是少数有完整英文成书 + 分数账的。
3. 确定性门禁解决的是事实连贯，不是好看。inkos 37 维审计仍被用户反馈滑回 AI 味。
4. **病不在检测不够多。** BestSeller 的 gate 数量是行业最重之一；再加词表不会自动变成高质量。
5. 中文网文开源（webnovel-writer / webnovel-director）**承认自己是网文工具**。BestSeller 的错位是对外通用、对内默认网文。

### 4.5 BestSeller 相对开源的位置（推断）

- **更像**：带 PostgreSQL 与多层门禁的中文网文生产平台。
- **不像**：autonovel 那种文学向单书研究管线；也不像 Novel-OS 那种中性编辑基础设施。
- **若产品目标是通用型小说平台**：需要把网文签约默认从横切层拿掉，改成按 `platform` / `genre` 显式选择。这是产品定位问题，不是缺 pack。

## 5. 题材参数传递与通用性泄漏

### 5.1 传递链（证据：能传到 writer）

```
ProjectCreate(genre, sub_genre, metadata.genre_intent_contract?)
  → resolve_project_create_writing_profile()     writing_profile.py
       ├─ forced_prompt_pack_key ← genre_intent_contract
       └─ infer_default_prompt_pack_key(genre, sub_genre)
  → build_project_metadata()  写入 prompt_pack_key / platform_target
  → drafts.generate_scene_draft
       └─ _resolve_prompt_pack_key(project)
       └─ render_prompt_pack_fragment + compile_methodology(...)
  → reviews.resolve_genre_review_profile
```

| 参数 | 是否到达 writer | 备注 |
|------|-----------------|------|
| `genre` / `sub_genre` | 是 | tone_keywords、infer pack、review profile |
| `prompt_pack_key` | 是 | metadata → fragments + methodology_compiler |
| `platform_target` | 是 | methodology scene rules + platform profile block |
| `genre_intent_contract` | 是（若存在） | 可 force pack，优先级最高 |
| taxonomy `pack_default` | 部分 | 仅当 keyword cascade 失败时 canonical fallback |

**断裂点不在「传不到」，而在「传到 writer 之前被默认值改写」。**

### 6.4 50 章完本验证（2026-08-17 文档，证据）

成书：《我把欺负我的人全排后面》131,356 字 / 50 章 / completed。

| 判据 | 验证书 | 修复前同题材 | 结论 |
|------|--------|--------------|------|
| hype 三字段非 NULL | 18/50 | 0/50 | 过 |
| 覆盖率 ≥ 同题材层 p10(0.17) | 0.18 | 0.16 | 过（对照本不过） |
| 时刻切片无回潮 | 0/50 | 1/50 | 过 |
| 零杀权 | 0 | 0 | 过 |
| 语义 payoff 中位 k=3 n=15 | 0.46 | 0.38 | **不可判别**（p=0.285） |

文档自己写的三条真实结论（对照时直接引用，不要改写成「修复成功」）：

1. 两本书都在后半段劣化。这是系统性问题。
2. 形状不同、总量相同。一本对一本不能把形状差异归因于修复。
3. 修订轮可能破坏早期爽点（盖戳与重算分叉）；需 k≥3 版本对测才能定罪。

量具局限：

- 跟人类比 → 只能用确定性分类器 + 题材分层（玄幻 0.23 / 市井 0.17 / 兜底 0.14）
- 自家书前后比 → 只能用语义判官且 k≥3、n≥20

## 13. 一页纸结论（对照完可回看）

1. **问题**：通用平台被网文横切默认劫持（合同 / 平台 / 爽文融合 / pack 推断），不是缺题材系统，也不是账单系列还在正文里。
2. **运行**：能启动、能接任务、当时空闲；无人值守会被门禁预算和 ABANDONED 打断。
3. **闭环**：结构闭环成立；读感闭环被 closure、软熔断、影子 judge、后半段劣化共同限制。
4. **门禁**：词表爽文判定**实现正确且不该有杀权**；真正的逻辑问题是密度加分奖励模板、以及签约合同对非签约书生效。
5. **对标**：开源里质量纪律更硬的是 Novel-OS（FAIL 停）和 autonovel（全书对抗修订）。BestSeller 更重、更像工厂，默认更偏向把书写完而不是写好看。
