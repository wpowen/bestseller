# 模型目录死条目治理（retired 标记 + 运行时死模型熔断上报）· 记录与验证 2026-08-08

## 一、诊断（真断点，非测量假象）

两个 NVIDIA NIM 目录条目上游已死，但框架仍把它们当活的卖：

| 条目 | 上游状态 | 实测报文（2026-08-08 live probe） |
|:---|:---|:---|
| `nim-deepseek-v4-pro` | 2026-08-07 EOL | `410 Gone — "The model 'deepseek-ai/deepseek-v4-pro' has reached its end of life on 2026-08-07T09:00:00Z"` |
| `nim-kimi-k2.6` | 已移除 | `404 Not Found — "Function '<uuid>': Not found for account '<id>'"`（litellm 包装为 `NotFoundError`） |

坏在三层（同族教训：2026-07「运行时 profile 指向死 qwen 多书卡死」——DB 看着正常，只在 worker 日志里可见）：

1. **可用性判定失明**：`model_catalog.py::_api_key_present` 只查 `api_key_env` 是否存在。两个死条目与 5 个活条目共用 `NVIDIA_API_KEY`，故恒 `available=True`，UI 照常可选、闸门照常放行。
2. **重试烧预算 + 污染共享 breaker**：`llm.py::_call_litellm_with_retry` 把 410/404 当普通瞬时错误按 `max_attempts=3` 重试，每次失败 `record_failure()` 进全局 `_llm_breaker`（阈 5 次 / 开 60s）——一个死模型的调用风暴会把 breaker 打开，殃及其他健康模型的正常调用。
3. **静默降级**：重试耗尽后 `complete_text` 落 `fallback_response` 静默文本，llm_runs 里只有 `provider=fallback`，没有「模型已死」的可查证据。

好消息：全 config 无任何默认配置引用这两个 key（判官用 `nim-mistral-large-3` / `minimax-m3`），只有测试当哑 key 用。

## 二、方案（soft/additive，无自伤硬闸门）

**标记退役而非删除**：条目留在 catalog 里，已选此模型的书得到显式「已下线」理由而非「Unknown id」。

1. **数据层**（`config/model_catalog.yaml`）：两条目加 `retired: true` + `retired_reason`（含日期与实测错误码）。
2. **Schema 层**（`model_catalog.py`）：`ModelCatalogEntry` 增 `retired` / `retired_reason` / `unavailable_reason`（计算字段）。可用性判定改为三段：`retired` → 运行时死模型登记表 → API key 存在性，每段给出人话原因。
3. **运行时熔断上报**（新增登记表）：`mark_model_runtime_dead(model, reason)` / `runtime_dead_reason` / `clear_runtime_dead_models`。进程内登记（重启即重探，故不会永久误杀）；登记后 `load_model_catalog` 对匹配 model 串的条目翻转 `available=False`，原因带「上游探测不可用」。
4. **错误码分类器**（`llm.py::_is_model_gone_error`）：410 恒真；404 需带 model/function 级标记（`function not found` / `does not exist` / NIM 实测的拆分短语 `Function '<uuid>': Not found`——由 live probe 抓出，单测已锁真实报文）。命中即：**不重试、不进共享 breaker、登记死模型、快速抛出**。
5. **显式上报替代静默跳过**：
   - `complete_text` 的 per-call/构思 override 遇不可用条目：warning 日志 + llm_runs metadata 落 `model_catalog_override_key` / `model_catalog_override_unavailable`（解决「只在 worker 日志可见」）。
   - 死模型 fallback 时 metadata 落 `model_gone: true`（DB 可查询 `metadata_json->>'model_gone'`）。
   - `resolve_project_model_entry` 对「已选但不可用」warning 一次（按 id 去重防刷屏）。
   - 两处选择闸门（`_set_project_model_payload` / 建书 payload 校验）错误消息带具体原因。
   - 前端下拉标签按原因显示「已下线」/「上游探测不可用」/「未配置 API Key」（取冒号前短语）。

**Live-probe 方案评估（未采纳阻塞式）**：在 `load_model_catalog` 加载路径做同步网络探测被否——该函数每次 UI 列表/每次 LLM 调用解析都会走到，网络探测会把 UI 与调用链的延迟绑在上游可用性上，且失败语义模糊（超时≠死）。采纳的替代：被动错误码熔断（上面 4）+ 手动探测脚本（`scripts/verify_model_catalog_dead_entries.py` D 段可作为半年度 catalog 体检工具，dead 端点探测零 token）。

## 三、三层验证

- **L1 单测**（新增 9 项 + 更新 2 项）：
  - `test_model_catalog.py`：退役条目带 key 仍不可用（同 key 活条目不受影响）/ resolve 跳过退役选择 / 缺 key 原因点名 env 变量 / 运行时登记表翻转可用性且不误伤同厂商其他条目 / 空 model 入登记表为 no-op。
  - `test_llm_services.py`：分类器正反例（410、NIM 双形态 404、误伤守卫：裸 404 与 500 与 429 均不判死）/ retry 层 fail-fast（1 次尝试、breaker 保持 closed、登记表记入）/ 死模型 fallback 落 `model_gone` metadata / 死 key override 落 skip metadata 且 mock 内容正常产出。
- **L2 回归**：`tests/unit` 全量 1968 passed, 5 skipped（含 concept_tournament 哑 key 换活条目、`nim-deepseek-v4-pro` 头部清除测试换 `nim-mistral-large-3`）。
- **L3 真机**（`scripts/verify_model_catalog_dead_entries.py`，19/19）：真 NVIDIA key 打真死端点。**首轮 16/19 抓出真 bug**：Kimi 实测 404 报文是 `Function '<uuid>': Not found for account`（拆分短语），分类器词表 `function not found` 连写不命中 → 3 次重试 + breaker 计数照旧。修分类器补拆分短语匹配后 19/19。再次印证「新增 LLM 调用必须真机冒烟」。

## 四、验收结论

- 直接用这两个 key：构思/评审调用在 llm_runs metadata 显式记 `model_catalog_override_unavailable=已下线：…`，用角色默认模型正常出活（非 fallback 文本）；选择类入口（建书表单/模型切换 API）直接拒绝并带原因。
- 未来再有模型死掉：首个 410/404 调用即 fail-fast + 登记 + catalog 翻不可用，不烧重试、不开 breaker、DB 可查 `model_gone`。
