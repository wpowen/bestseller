## 0. 一页结论

本轮落地三件事：**per-book 生成单元开关**（T2.1）、**章内连贯性检查器**（T1.1）、以及把检查结果**接进修复提示**（否则检出即浪费）。Docker 栈已重建，容器内 7 项生效核验通过，端到端真机冒烟（真 LLM）阳性检出 / 阴性零误报。

调查中发现计划里的 M2 核心其实**已存在一半**：整章路径的修复不是只会整章 re-roll，`_create_chapter_first_local_auto_repair_task` + `rewrite_chapter_from_task` 已经是"局部 patch 优先"路径（`pipelines.py:8110-8137`）。因此原计划的 T2.4-T2.6（分段重写）降级为"接线到既有 patch 路径"，工作量大幅缩小。

## 2. 为什么建这个门：缺口先实证再动手

计划里写了"新检查器须先证明现有 gate 族拦不住此病"。用整章模式**唯一实测输掉的那一案**（称"低筋面粉"、和面用"高筋面粉"，4:0 落败）跑现有门禁：

```
样本含低筋: True  含高筋: True
common_sense findings: 无
deterministic audit: {'ENDING_HOOK_MISSING': 1}   ← 无关项
```

现有 `common_sense_gate` 只覆盖时间算术/倒计时/出血/时代错置等硬编码模式，`CanonStateRegressionCheck` 管的是跨章 canon。**没有任何一条覆盖"章内具名物件属性前后翻转"**。缺口成立。

## 3. 设计取舍

| 取舍 | 理由 |
|---|---|
| **advisory，永不 block** | 该库已被一个允许 block 的检查器误报毙过书（NAMING_OUT_OF_POOL）。LLM 矛盾检测有真实误报率 |
| **证据必须原文落地** | 每条 finding 必须给出两句**能在正文里找到**的原句；模型转述即丢弃。转述正是误报的形态。匹配时剥标点空白容忍模型改写标点，但剩余字符仍须逐字有序命中 |
| **类别白名单** | 只认 object/quantity/name/body_state/time/place 六类，幻觉出的类别直接丢——否则可以凭空发明一个修复范围 |
| **fail-open** | 任何传输/额度/解析失败都返回空报告 + `skipped_reason`。不能让一次 advisory LLM 调用决定一本书的生死 |
| **不查文笔/节奏/AI腔** | 那些有别的评审负责。单一职责，也避免与反AI腔真源重复计费 |

成本：每章多一次 critic 调用。整章模式生成调用本来就是场景模式的 1/3（实测 9→3），加一次仍净省。

## 5. 冒烟测抓到的两个真 bug（离线测试测不出来）

两个都会让门禁"看起来在跑，实际永远零命中"——比崩溃更危险：

1. **`fallback_response` 未传**：`LLMCompletionRequest` 该字段必填，缺失时 pydantic 直接抛 ValidationError。上线即每章异常（被 `except Exception` 吞成 debug 日志）。
2. **`completion.text` 字段名错**：结果模型的字段是 `content`。原代码用 `getattr(completion, "text", "")`，**静默返回空串** → 每次都 `unparseable_response` → 检查器永远零命中且毫无报错。

已加两条守卫测试锁定（真实构造 request、断言结果模型字段名）。教训固化：**`getattr(obj, "field", default)` 用在自己代码的必需字段上，是把类型错误变成静默降级的最快方式**。

### 真书暴露的三个自伤（都是本轮新代码的问题）

**① best-of-N 挂错出口，从未执行。** 钩子在"自动修复预算耗尽"（`pipelines.py` 8578/8698），而真书全部经由**章评审 quality_debt** 出口（10052/10085/10317）退出。补钩时自己写的测试又抓到漏了第三个出口（`chapter_rewrite_revision_limit`，恰恰是最该选优的时刻）。现已覆盖全部 4 个出口。

**② 选优逻辑在真实数据上无效。** ch4 四版 1385/1635/2030/1772，**v3 是唯一过 1800 硬下限的版本却没被采用**，章节因太短 blocked；而**四版全部没有质量分**——原实现 `JOIN quality_scores` 会查不到任何行、直接 no-op。已改 `OUTER JOIN` + 排序规则改为 **(过硬下限, 质量分, 版本号)**：字数硬合同确定性可得，LLM 评分不是；跌破下限的稿无论分多高下游都会毙，凭分选它严格更差。用 ch4 真实数据写了回归测试。

**③ 连贯性检查器误报率 2/3（ch6 首次命中）。** 逐条人工核验：
- ✅ 真阳性：3:31 写"七分钟够他走回前台"，3:31:40 已走进前台大厅——自称七分钟的路 40 秒走完。
- ❌ 误报 ×2（同一处报两遍，`first_evidence` 相同）：筐里 4 封信，后文反复提"那只牛皮纸信封"被判成"只剩一封"。这是**叙事聚焦**，正常写法。
- 修：prompt 补"叙事聚焦不是数量矛盾"排除条款；代码按 `first_evidence` 归一化去重（prompt 是软约束，结构性去重才可靠）。

### 尚未处理的观察
- **`ENDING_HOOK_MISSING` 三次命中整章样本**（bakery 样本 + 本书 ch1 + …）。ch1 正文实际有钩子（无声开走的面包车、签着主角笔迹与指印、日期是昨天的登记表），但检测器只看**最后 120 字**，钩子落在结尾前一两段、后接收束意象。这是**验收口径与整章生成风格不匹配**，不是简单误报。**未动阈值**——样本量不足以推翻门禁（本库有"ch9=0.80 勿放宽阈值"教训），正确下一步是拉多章正文人工核验，判断改检测口径还是改 prompt 收尾要求。
- 正文漏出 markdown 标题 `# 第1章 …`，prompt 明令禁止 `#` 标题，硬约束未被遵守。
- 本次跑的书用的是**加钩子/改排序之前的镜像**：它的价值是提供真实故障数据，不是验证修复有效。验证修复需 rebuild 后重跑。

### 方法论结论
三层验证各自的盲区被这轮完整暴露：单测证明代码存在且可调用；容器冒烟证明依赖契约正确；**只有真书能证明代码在真实控制流里会被走到、且逻辑对真实数据有效**。本轮四个问题全部只在后一层暴露，前一层均"全绿"。
