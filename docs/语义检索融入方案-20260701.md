## 一、借鉴思路在当前框架中的落点

goink 的"本地语义搜索"解决的是"AI 用不同措辞问同一件事时，能不能认出这是同一件事"。这个问题在我们框架里**不是发生在质量闸门里**（调研已确认 `canon_guardrails.py`/`payoff_ledger_gate.py`/`world_law_consistency_gate.py`/`cross_kernel_consistency_gate.py` 全部是正则/关键词/LLM 判断，完全不经过 `retrieval.py`），而是发生在**写手拿到"已建立事实"的那一刻**：

| 调用点 | 文件:行 | 作用 | 语义检索缺失的后果 |
|---|---|---|---|
| `build_scene_writer_context` | `context.py:1067` | 场景正文写手 prompt 组装时，检索相关已建立事实/伏笔/人物设定塞进上下文 | 如果场景要写的内容与已建立事实"意思一样但措辞不同"，检索召回不到，写手在**没看到设定的情况下**凭空写，容易漂移/矛盾 |
| `build_chapter_writer_context` | `context.py:2083` | 章节直写模式同上 | 同上 |
| `search_story_context`（LLM 工具） | `query_broker.py:372` | 写作过程中模型主动查"这件事之前提过吗" | 模型换一种问法查询就可能查不到，等于工具失效 |
| `retrieval_search`（CLI 调试） | `cli/main.py:2891` | 人工排查用 | 排查时也会被同样的假阴性误导 |

**结论**：这不是给某个闸门加新能力，而是**修复现有检索链路的召回率**——检索结果直接决定写手能看到多少"已经写过的设定"，召回率低=写手更容易凭空编造导致人设/伏笔/世界观漂移，这正好是本框架长期在治理的"漂移类"问题（对照 memory 里的画像漂移、跨书同质化等根因，本质都是"生成时看不到/对不齐已有约束"）。所以这处修复预期收益是**降低需要 audit_loop 事后修复的漂移类问题密度**，属于结构性质量提升，不是锦上添花。

## 二、完整融入方案

### 现状（已确认的关键事实）

- `RetrievalChunkModel.embedding` 是 **pgvector `Vector(1024)` 固定维度列**（`infra/db/models.py:1481`），另有 `embedding_model`（每行文本标签）、`embedding_dim`（每行整数）两个**逐行元数据字段**——这两个字段已经预留了"不同行可能来自不同 backend"的可能性，只是目前从未被用出这个语义。
- 写入路径唯一入口：`_upsert_source_chunks`（`retrieval.py:154-192`），固定调用 `build_hashed_embedding`。
- 查询路径：`search_retrieval_for_project`（`retrieval.py:498` 附近）同样固定调用 `build_hashed_embedding` 构造 query 向量。
- `RetrievalSettings`（`settings.py:86-96`）目前没有 backend 开关。

### 设计原则

1. **默认行为零变化**：新增能力必须是 opt-in，不动现有 `embedding_backend` 默认值就与今天完全一致。
2. **不做危险的 in-place 数据迁移**：不重写已有 1024 维哈希向量的语义；混用会让 cosine 相似度失去意义。
3. **复用 hybrid 打分的"取 max"设计天然做安全网**：`_score_chunk`（`retrieval.py:141`）里 `semantic_score = max(vector_score, lexical_overlap * 0.85)`——这意味着即使语义向量质量不如预期，词面重叠这条底线分还在，不会比现在更差，只会更好或不变。

### Phase 1（低风险，零迁移，用于验证真实收益）

**技术手段**：语义模型（`paraphrase-multilingual-MiniLM-L12-v2`）输出 384 维单位向量，**零填充到 1024 维**再写入现有列。因为原向量已归一化，零填充不改变模长，填充后的余弦相似度与填充前的 384 维余弦相似度**数值完全相等**——可以证明：`dot(pad(a), pad(b)) = dot(a,b)`，`norm(pad(a)) = norm(a) = 1`。所以不需要改列宽度。

**具体改动**：

1. `settings.py` — `RetrievalSettings` 新增字段：
   ```python
   embedding_backend: Literal["hashed", "semantic"] = "hashed"
   semantic_model_name: str = "paraphrase-multilingual-MiniLM-L12-v2"
   ```
2. `retrieval.py` 新增一个统一入口，替代直接调用 `build_hashed_embedding`：
   ```python
   def build_embedding(text: str, settings: AppSettings) -> list[float]:
       if settings.retrieval.embedding_backend == "semantic":
           vector = build_semantic_embedding(text, model_name=settings.retrieval.semantic_model_name)
           if vector is not None:
               return _zero_pad(vector, settings.retrieval.embedding_dimensions)
           # 模型/依赖不可用（如离线容器未预装权重）→ 降级，绝不静默产生错误结果
           logger.warning("semantic backend unavailable, falling back to hashed embedding")
       return build_hashed_embedding(text, settings.retrieval.embedding_dimensions)
   ```
   `_upsert_source_chunks` 和 `search_retrieval_for_project` 里的 `build_hashed_embedding(...)` 调用替换为 `build_embedding(chunk_text, settings)`。
3. **写入时打标**：`embedding_model` 字段写入 `f"semantic:{settings.retrieval.semantic_model_name}"`（而不是当前的 hashed 模型名），这样每一行都能追溯自己是哪个 backend 产出的。
4. **禁止半新半旧的项目级混用**：在 `refresh_story_bible_retrieval_index` / `ensure_project_retrieval_index` 入口加一道检查——若该 project 已有 chunk 的 `embedding_model` 前缀与当前 settings 配置的 backend 不一致，强制走全量重建（先 delete 该 project 全部 chunk 再重新 upsert），不允许增量追加导致同一 project 内一部分行是哈希向量、一部分是语义向量（那样 top-k 排序会比较两种不可比的分数，结果是噪音）。

**这一步不需要 Alembic 迁移**——`embedding` 列类型、维度都不变，只是内容来源和 `embedding_model` 标签变了。

### Phase 2（验证收益后，正式化）

如果 Phase 1 canary 证明有效（见下方自测方案第 L3 节），再做"体面"的长期方案，避免长期依赖零填充这种技巧：

1. Alembic 迁移新增列 `embedding_semantic vector(384)` + 对应 `idx_retrieval_chunks_embedding_semantic`（hnsw, cosine），仿照 `migrations/versions/0032_chapter_indexes.py` 的写法风格（先建列，索引单独一条 `op.execute`）。
2. `_score_chunk` 按 `chunk.embedding_model` 前缀选用对应列参与打分，两个 backend 可以在同一 project 内针对不同 `source_type` 分别选用（比如结构化事实用语义列，海量正文草稿仍用哈希列，见下方成本考量）。
3. 移除 Phase 1 的零填充 trick，`embedding_backend` 从"项目级二选一"升级为"按 source_type 可分别配置"。

### 成本与范围控制（重要，不能无脑全量切换）

- 语义模型是神经网络推理，CPU 编码一个 chunk 大约几十毫秒级别（相对哈希词袋的微秒级是数量级差距）。全量对所有 `scene_draft`/`chapter_draft` 正文重新分块编码，在批量生成场景下会显著拖慢索引刷新。
- **建议 Phase 1 canary 范围只覆盖 `source_type in ("character", "canon_fact", "relationship", "world_rule", "scene_context")`**——这些恰好是"结构化事实类"，量小（每本书几十到几百条），复述改写导致漏召回的代价也最高（人设/世界观矛盾）。`scene_draft`/`chapter_draft`（海量原文）留在哈希 backend，价值密度低、成本高。
- 模型权重（约 470MB）需要在离线容器部署环境里预先烘焙进镜像或挂载缓存卷，不能依赖运行时联网下载（对照 memory 里"容器内跑"的部署习惯，运行时打 HuggingFace Hub 请求是不可接受的隐式网络依赖）。

## 三、使用方案

### 配置开关

```yaml
retrieval:
  embedding_backend: semantic   # 默认 hashed，不改就是今天的行为
  semantic_model_name: paraphrase-multilingual-MiniLM-L12-v2
```

按 project 级 canary：优先只在单个 project 的运行配置里打开（如果配置支持 project 级 override），不做全局默认切换。

### 触发重建索引

复用现有检索刷新入口，不需要新命令：
- `refresh_story_bible_retrieval_index` 已经是"先删后插"的全量重建语义，切换 backend 后照常调用即可（第二节第 4 点已加的 backend 一致性检查会自动强制全量重建，避免半新半旧）。
- 建议在 `cli/main.py` 现有 `retrieval_search` 命令旁新增一个只读诊断子命令（例如 `retrieval reindex-status --project <slug>`），输出该 project 当前 chunk 表里各 `embedding_model` 值的行数分布，方便运维确认"这个项目现在到底是哪个 backend"，避免混淆。

### 运行时行为

- `build_scene_writer_context`/`build_chapter_writer_context`/`search_story_context` 三个消费方**代码不用改**——它们调用的是 `search_retrieval_for_project`，只要该函数内部改成走统一的 `build_embedding` 入口，语义能力就是透明生效的。
- 降级路径已内置：模型/依赖缺失时自动退回哈希 backend 并打 warning 日志，不会导致运行时报错或整本书失败（对照 memory 里反复出现的"无界/硬阻断拍死整本"教训，这里刻意做成软降级）。

### 灰度节奏建议

1. 先在本地/测试环境用现有 `retrieval_search` CLI 对同一 project 跑一组人工构造的复述查询，人工确认召回结果符合预期。
2. 选 1 本正在生产的书（题材优先选设定复杂、人物关系密集的，比如群像/多势力玄幻——复述失配代价最高），只对该 project 打开语义 backend，观察 `audit_loop` 后续几章的漂移类问题密度是否下降。
3. 无异常后再考虑扩大 canary 范围；是否推广到全局默认仍需数据支撑，本方案不预设一定要转正。

## 四、自测方案

按现有开发规范（memory: [开发与验证标准](../.. )——强制五阶段+三层验证：L1 单测含 no-op、L2 git-stash 归因、L3 真机 live 栈验证）设计：

### L1 单元测试（新增/扩展）

- 已有 `tests/unit/test_semantic_embedding.py`（3 项，已通过）：验证语义 backend 本身的正确性 + 无文本/无依赖时返回 `None` 的降级契约。
- 新增 `tests/unit/test_retrieval_services.py` 补充用例：
  1. **no-op 回归测试**：`embedding_backend="hashed"`（默认值）时，`build_embedding(text, settings)` 与直接调用 `build_hashed_embedding(text, dim)` 结果逐位相等——证明本次改动对默认路径零影响。
  2. **零填充正确性**：构造一个 384 维单位向量，`_zero_pad` 到 1024 维后，`cosine_similarity(pad(a), pad(b))` 与用未填充的 384 维向量直接算的 cosine 相等（数值断言，容差 1e-9）。
  3. **降级路径**：mock `build_semantic_embedding` 返回 `None`（模拟依赖缺失），断言 `build_embedding` 自动落回 `build_hashed_embedding` 的结果，且不抛异常。
  4. **backend 一致性检查**：用 `FakeSession` 模拟一个 project 已有 `embedding_model="hashed-crc32"` 的历史 chunk，配置切到 `semantic` 后调用 `refresh_story_bible_retrieval_index`，断言触发了全量 delete-then-insert（不是增量 upsert），且新行的 `embedding_model` 前缀是 `"semantic:"`。
  5. 沿用 `FakeSession` mock（`test_retrieval_services.py:21` 的既有模式），`build_semantic_embedding` 用 `unittest.mock.patch` 打桩，**不在 CI 里真跑模型**（避免下载/网络依赖拖慢单测），真模型验证放到 L3。

### L2 git-stash 归因验证

用一份"复述对照集"量化对比改动前后的检索召回率，确认收益确实来自这次改动而非噪音：

1. 从已有生产项目的 `CanonFactModel`/`CharacterModel` 里抽取 20-30 条真实已建立事实，人工为每条写一句"换个说法的复述"和一句"无关但词面有重叠的干扰句"（复用调研文档里的方法论）。
2. 写一个 bench 脚本（放 `scratchpad`，不入库）：对每条事实分别用当前生产代码（`git stash` 前）和改动后代码算 `recall@top_k`（复述句能否排进 `settings.retrieval.top_k` 内）。
3. `git stash` 切回改动前跑一遍基线，`git stash pop` 切回改动后再跑一遍，对比两次 recall 曲线——这一步的意义是排除"模型本身运气好/样本选择偏差"，确认差异是改动本身带来的，不是环境噪音。
4. 期望结果：语义 backend 的 recall@top_k 显著高于哈希 backend（对照文档里单点验证已经是 0.85 vs 0.14 的量级差距，20-30 条样本的平均值预期同样显著）。

### L3 真机 live 栈验证

1. **零 token 打桩确认接线正确**：在真实 web/worker 容器里，把 `settings.retrieval.embedding_backend` 切到 `semantic`，`semantic_model_name` 指向一个本地已缓存的小模型，先只跑 `retrieval reindex` + `retrieval_search` CLI（不触发正文生成、不消耗 LLM token），确认索引重建成功、`embedding_model` 字段写入正确、语义查询返回预期召回结果。
2. **端到端验证**：挑一个真实在跑或新开的 project 做 canary（按第三节灰度节奏），实际生成若干章，人工核对 `build_scene_writer_context` 组装出的写手 prompt 里是否包含了此前哈希 backend 会漏召回的复述类设定引用。
3. **性能基线**：对比开启前后 `refresh_story_bible_retrieval_index` 的耗时（单个 project 全量重建），以及 `search_retrieval_for_project` 单次查询延迟，确认在可接受范围内（不应显著拖慢构思/写作阶段的响应时间——对照 memory 里"构思超时踩 watchdog"的历史教训，任何新增的同步阻塞调用都要量化耗时）。
4. **回归确认**：默认配置（`embedding_backend="hashed"`）下跑一次现有全量单测套件 + 抽查 1-2 本历史项目重新走一遍构思/大纲/正文生成，确认零回归。
5. **离线部署确认**：验证模型权重已烘焙进容器镜像/挂载卷，断网状态下语义 backend 仍能加载（不依赖运行时联网），否则必须验证降级路径能正确触发且不拍死任务。
