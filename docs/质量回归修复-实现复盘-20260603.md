## 2. 发现的问题点

### P1 ❗HIGH — WS-B 把完整性块提到"永不裁剪"的 Tier 1，导致连续性饿死
- **现象**：我把 6 个完整性守护块 + 2 个硬合同块塞进 Tier 1（Tier 1 从 17 → 25）。Tier 1 **从不裁剪**。
- **实测复现**（内容密集章，每块取真实可达的大小）：
  ```
  Tier1 合计 = 12,400 token  > 8,000 预算
  recent_scene_section (近期场景连续性) → DROPPED
  emotion_track_section / clue_section → DROPPED
  最终 prompt = 12,400 token（预算根本没兜住）
  ```
- **危害**：`recent_scene_section` 是跨场景连续性的关键上下文，被丢弃 = writer 不知道上一场刚发生什么 → **正文段落断裂**，正是用户最初抱怨的"读不通"。即：**我把"过载"换成了"丢连续性"，可能并没真正改善连贯度**；且 Tier 1 无上限时预算形同虚设。
- **根因**：Tier 1 塞太多 + Tier 1 无内部上限；完整性块（canon/timeline/character_role）其实与 `story_bible/hard_facts` 部分重复，不该全部"永不裁剪"且优先级高于连续性。

### P2 ❗HIGH — B2「单块长度上限」未实现
- 计划要求每块 ≤600 字，避免单块膨胀。实际只有少数块经 `_compact_json_block/_compact_text_block`（1400/1000 字）压缩，**完整性块（canon/timeline/character_role）无统一上限**。
- 后果：单个大 canon 块即可吃光预算，是 P1 饿死的直接放大器。

### P3 ⚠️MEDIUM — 章节级写作路径（chapter-first）未纳入逐块预算
- `build_chapter_first_draft_prompts`（`_enrich_chapter_first_context` 注入的 21 块）**不走** `_budget_context_sections`，而是先拼全量再用 `_soft_trim_user_prompt` 做字符级"头+尾"粗裁（代码注释 8115 自承"真正的逐块预算应调用 `_budget_context_sections`"）。
- 后果：若任何流程走 chapter-first 写作，仍是 21 块全量、只在超 `budget×3` 字符时粗暴砍中段。诊断的书走的是 scene 路径，故本次没踩雷，但这是**同类隐患未覆盖**。

### P4 ⚠️MEDIUM — WS-A 的 A3「fail-soft」未实现
- `planner.py:1804` 的"chapter-outline repair loop after N attempts"硬失败逻辑仍在。当前只修了"dict refs"这一**已知**畸形；若模型对**其它**非关键字段产出新畸形，仍可能 3 次重试后失败 →（潜在）整盘重启。
- 即 WS-A 的鲁棒性依赖"coercion 覆盖所有畸形"，没有"非关键字段失败就丢弃+warning"的兜底。

### P5 ℹLOW — WS-B 只省 token，不省"算"
- 被预算裁掉的 advanced 块（voice_dna/diversity/signature_scene…）仍在上游 `_enrich`/orchestrator 里**照常计算**（DB/LLM 调用）再丢弃。
- 后果：prompt 变小（利于质量），但**单场景生成耗时没因此下降**；计算这些块的时间仍在。

### P6 ℹLOW — 函数默认预算与配置不一致
- `build_scene_draft_prompts`/`build_chapter_first_draft_prompts` 默认 `context_budget_tokens=6000`，而 config 是 8000。当前调用方显式传 8000 故无碍，是潜在埋点。

## 3. 修复计划（按优先级）

### F1（HIGH，对应 P1）重排优先级，保住连续性，给预算真正封顶
- **缩小 Tier 1**：只保留真正小而必需的硬约束——`contract_section / current_scene_contract_line / hard_fact_line / identity_line / chapter_length_line / qimao_opening_contract_line`。
- **完整性守护块 + 连续性同列 Tier 2**：把 `canon_guardrails / timeline_canon / scene_coherence / character_role` 与 `recent_scene_section / emotion_track / clue_section` 一起放 Tier 2（预算内、优先于 advanced garnish），让两者**公平竞争预算**，而不是完整性永远赢、连续性永远输。
- **给 Tier 1 封顶**：即使 Tier 1 也要参与一个上限（如超预算 80% 触发对 Tier-1 内大块做 B2 压缩），保证预算能兜住。
- **测试**：内容密集章（Tier1 大）下，断言 `recent_scene_section` **不被丢弃**，且总 prompt ≤ 预算×1.1。

### F2（HIGH，对应 P2）实现 B2 单块上限
- 在 `_budget_context_sections` 入口或渲染层，对每个 section 先做 `max_tokens`（如 700）截断（保留头部+关键尾），再进预算。
- 让 canon/timeline/character_role 等也受单块上限约束。
- **测试**：单块 5000 字 → 截断到 ≤700 token；截断后仍含关键首句。

### F3（MEDIUM，对应 P3）chapter-first 路径接入逐块预算
- 让 `build_chapter_first_draft_prompts` 把 21 个 block 组成结构化 `ctx` dict，过 `_budget_context_sections`（复用同一套 tier），替代/前置于 `_soft_trim_user_prompt`。
- **测试**：构造 21 块全满，断言 chapter-first prompt ≤ 预算且保留 core 块。

### F4（MEDIUM，对应 P4）实现 A3 fail-soft
- 在 volume-outline 校验失败时，区分**关键骨架**（章数/标题/goal）与**非关键 worldview 字段**：后者校验失败 → 丢弃该字段 + 记 warning 继续，不计入"repair loop 失败"、不触发 `restart_superseded`。
- **测试**：非关键字段畸形 → 产出有效 outline + warning，无重启。

### F5（LOW，对应 P5）按 lean 跳过 advanced 块的"计算"
- 在 `pipelines.py`/`_enrich` 计算 advanced 块前判断 lean，lean 下直接不算（省时），与预算裁剪形成"算前就省 + 算后兜底"双层。

### F6（LOW，对应 P6）统一默认预算
- 把两个 builder 的默认 `context_budget_tokens` 改为读 settings 或与 config 一致（8000），消除埋点。

### F7（P1 延续）WS-C 重写收敛 + 闸门分层（独立 PR）
- 维持原计划：`gate_registry` 加 `tier`，advanced gate 改 warn 不 rewrite；确保外层 repair 不重置单场景重写计数。

## 4. 建议执行顺序
F1 + F2（同改 `_budget_context_sections`，一起做并补测试）→ F4（规划鲁棒性）→ F3（覆盖 chapter-first）→ F5/F6（优化）→ F7（独立 PR）。

**F1/F2 是必须的**：当前 WS-B 在内容密集章下可能用"丢连续性"替换了"过载"，未必真改善连贯度——必须先把这个回归修掉再做端到端验证书。

# 附录 · WS-C 实现复核（2026-06-03）

> 对象：工作区 `gate_registry.py` / `pipelines.py` / `drafts.py` / `settings.py` 的 WS-C 改动 + 配套报告。
> 结论：分层框架与 churn 收敛**主体正确且有价值**，但发现 **2 个真实缺陷**（报告未承认），还有若干需澄清项。

## WS-C 正确的部分
- `GateTier` + `tier` 字段为纯加法、默认 `core`，向后兼容；`core/advanced` helper 与分区测试（core∪advanced=全集、互斥）正确。
- 运行时 block 谓词切到 `core_block_metadata_keys()`，overview 仍用全集——设计合理。
- C3 单场景 counter 放 `scene.metadata_json` 且不在 residue 清理范围 → 跨 `project_repair` 不重置，churn 能收敛。**方向正确**。

## ❗WS-C 缺陷

### CD1 ❗HIGH — `material_referential_integrity_gate` 标识符被改坏（基于错误前提）
- 报告 §4.1 自称"修复历史拼写错误 → 正确命名"，**实际相反**：
  - HEAD 原本是正确的 `material_referential_integrity_gate`（全下划线）；文件名也是 `material_referential_integrity_gate.py`（全下划线）。
  - WS-C 把它改成**含空格**的 `"material_referential integrity_gate"`，block key 也变成 `"blocked_by_material_referential integrity_gate"`（空格）。
  - 代码注释（gate_registry.py:61-64）声称"文件名是空格分隔的"——**该前提与事实不符**（文件名是下划线）。
- **影响**：这是 **core** 门。全仓库其它地方（含 `book_lifecycle_quality_gate.py:915`、HEAD 约定、所有 `blocked_by_*` 写入点如 `"blocked_by_anti_meta_gate": True`）都用下划线约定。空格版 key 只存在于 gate_registry 自身——意味着任何按下划线约定写入的 block metadata **不会被 `core_block_metadata_keys()` 匹配** → 这个结构性完整性门可能**静默失去 block 能力**。
- **测试掩盖**：`test_gate_registry.py:69` 在 `isdisjoint` 检查里用的是下划线名（该断言恒真、并不校验真实门名）；:94 又把空格 block key 锁成期望值，:92 注释重复了同一错误前提。**测试"全绿"≠ 标识符正确**。

### CD2 ❗HIGH — 把"时间线连续性"门误判为"polish"并降级 warn-only
- WS-C 把 `phase_d_time_gate` 归入 advanced（warn-only），`pipelines.py:691` 注释甚至写"(material_advancement, phase_d_time) are polish/signature/style checks"。
- 但 `phase_d_time_gate` 实跑的是 `check_countdown_arithmetic`（倒计时算术一致性）+ `check_time_regression`（时间倒流检测）——这是**时间线正确性/连续性**校验，**不是 polish**。
- **影响**：降级后时间矛盾（如倒计时 4:12 之后又变 5:00、第 5 章发生在第 4 章之前）**不再 block，直接进正文** → 直接加重用户最初抱怨的"逻辑不清晰"。**与本次修复目标相悖。**
- `material_advancement_gate`（校验"本章必须出现的 reveal/规则/证据是否落地"）同理偏 correctness，降 warn 可能放行"空转章"。这两个的降级需重新评估。

### CD3 ℹLOW — C3 可能在单次 repair pass 内对同一 scene 多次 bump
- 3 个 reset 循环（write-safety / metadata-code / length-stability）若同一 scene 命中多类 block，会在一次 pass 内多次 `claim_scene_auto_repair_attempt` → counter 超过"真实重写次数"。
- **方向安全**（过计数 → 更早收敛，符合"关 churn"目标），但 `total_attempts` 语义不等于"重写版本数"，验收口径需说明。

### CD4 ℹINFO — 报告对 WS-B 的"协同"基于一个仍带回归的 WS-B
- WS-C 报告 §6 复述"WS-B 17.7k→7.5k 已完成"，但未纳入本复盘 P1（连续性饿死）/P2（单块无上限）。即 WS-C 是在一个**尚有回归的 WS-B** 之上叠加的。

## WS-C 修复计划（接续 §3 的 F 列表）
- **F8（HIGH，CD1）**：把 `material_referential_integrity_gate` 的 name 与 metadata keys 全部改回**下划线**（与文件名/HEAD/全仓库一致）；同步改 `test_gate_registry.py:92-94` 注释与断言；核对是否真有写入点、确认 core 门 block 能力恢复。
- **F9（HIGH，CD2）**：把 `phase_d_time_gate` 移回 **core**（时间线连续性属 correctness）；重审 `material_advancement_gate` 归属；改正 `pipelines.py:691` 的错误注释。补测试：时间倒流/倒计时矛盾仍触发 block。
- **F10（LOW，CD3）**：明确 counter 语义（每 pass 至多 +1，或文档说明 total_attempts≠版本数）；选择其一并补测试。

## 修订后的总执行顺序
F1+F2（WS-B 饿死/单块上限，必做）→ **F9（时间线门移回 core，止血"逻辑不清晰"）→ F8（标识符改回下划线）** → F4（A3 fail-soft）→ F3（chapter-first 预算）→ F10/F5/F6（收尾）。
